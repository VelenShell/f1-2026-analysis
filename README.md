# F1 2026 — аналіз середини сезону

Прогноз особистого чемпіонату на основі даних перших 11 етапів сезону 2026.

## Чому саме зараз і саме так

2026 — рік зміни регламенту. Це означає, що дані попередніх сезонів як основа
для прогнозу не працюють: машини інші, двигуни інші, розстановка сил інша.
Референсний аналіз, зроблений у березні за підсумками однієї гонки, це
проігнорував — і промазав по чемпіону.

Літня пауза дає те, чого не було в березні: **пів сезону реальних даних
нового регламенту**. На них можна не вгадувати, а вимірювати.

## Що аналізуємо

Основний фокус — **особистий залік**. Кубок конструкторів згадуємо коротко.

1. **Темп машин, очищений від сміття.** Час кола сам по собі брехливий: у ньому
   сидить паливо, вік гуми, сейфті-кар і трафік. Рахуємо кола з поправкою на
   паливний тренд і компаунд, викидаючи кола під SC/VSC (`race_control`) і
   виїзди з піт-лейну (`is_pit_out_lap`).
2. **Дуелі напарників.** Єдине чисте вимірювання пілота — той самий болід.
   Расселл vs Антонеллі і є відповідь на питання, чому березневий прогноз
   промазав.
3. **Прискорення на прямих.** Головна технічна інтрига 2026 — менеджмент
   енергії за новим регламентом. Крива швидкості по довгій прямій показує, в
   кого тяга сідає в кінці, а в кого ні.
4. **Проходження поворотів.** Каталог поворотів будується автоматично з
   кривизни траєкторії (`location`), не руками. Порівняння — тільки між
   напарниками, 3–4 репрезентативні траси.
5. **Погода і сходи.** Гіпотеза «жара вбиває машини» на рівні гонок **не
   підтверджується** (r = 0.19 при n = 11). Правильний тест — на рівні
   «пілот × гонка» (242 спостереження) з контролем типу траси. Може вийти
   негативний результат; так і покажемо.
6. **Монте-Карло на 12 гонок, що лишились** → ймовірність титулу.
7. **Бектест березневого прогнозу** на реальному пів-сезоні.

## Обмеження даних (перевірено, не припущення)

- **OpenF1 має тільки 2023+.** Довга історія — через Jolpica. При зміні
  регламенту вона все одно майже марна, тому свідомо мінімізована.
- **Причини сходу немає.** OpenF1 дає лише `dnf: true/false`. Jolpica на 2026
  віддає грубі статуси (`Finished / Lapped / Retired / Did not start`) без
  класичних деталей типу `Engine` чи `Overheating`. Тому «загорілись від
  спеки» прямо довести не вийде — тільки частоту сходів проти температури.
- **Частота телеметрії:** `car_data` 3.6 Гц, `location` 4.2 Гц. Швидкість в
  апексі й прискорення міряються надійно; **точка гальмування — ні** (при
  250 км/год це точка кожні ~17 м).
- **Rate limit:** публічно 3 req/s. Авторизація дає запас, історичні дані від
  цього не залежать — вони повністю безкоштовні.
- **Сходи цього сезону: 44 на 242 старти = 18%.** Для сучасної Ф1 це дуже
  багато (норма ~7%). Будь-який прогноз, що ігнорує сходи, — фантазія.

## Структура

```
ingest/fetch_openf1.py   нічний харвестер (тільки httpx + stdlib, резюмиться)
data/raw/                сирі дані, jsonl.gz
data/logs/fetch.log      лог завантаження
sql/                     схема Postgres + завантаження
analysis/                моделі: темп, напарники, телеметрія, Монте-Карло
notebooks/               розвідка
```

## Завантаження

```bash
./.venv/bin/python ingest/fetch_openf1.py     # резюмиться, можна перезапускати
./.venv/bin/python ingest/status.py           # що вже завантажено
```

Харвестер тягне даними в порядку цінності: спершу легкі ендпоінти 2026
(на них будується весь аналіз), потім 2025 як база для порівняння, потім
телеметрія — гонки, квали, практики, тестові дні останніми. Якщо прогін
обірветься, найважливіше вже на диску.

## Розподіл роботи

Python + Postgres — тут. Power BI і презентація збираються окремо.
Факт-таблиці свідомо лишаються з сирими метриками, без пре-агрегації —
щоб ранкінги, частки й прогнозні міри рахувалися в DAX.

## Фінальний аналіз

`final_project.ipynb` — повний аналіз у п'яти частинах: завантаження й очищення,
описова статистика, перевірка гіпотез, моделювання та прогноз, телеметрія.

Ноутбук читає CSV із `export/`, тому відтворюється без доступу до PostgreSQL:

```bash
python -m venv .venv && ./.venv/bin/pip install pandas numpy scipy seaborn matplotlib scikit-learn jupyter
./.venv/bin/jupyter lab final_project.ipynb
```

Частина 5 читає телеметрію напряму з PostgreSQL (74 млн рядків, у CSV не поміщаються),
решта працює з CSV із `export/`.

Ключові результати: перевага Антонеллі над напарником 0.432 с/коло (p = 0.003),
розкид темпу по пітлейну 4.8% проти звичних 2%, 81% дисперсії темпу припадає на машину,
ймовірність титулу Антонеллі ~97% зі стійкістю до подвоєння розкиду. Каталог поворотів
будується автоматично з кривизни траєкторії: на Хунгароринзі знайдено рівно 14 поворотів,
стільки ж, скільки насправді.
